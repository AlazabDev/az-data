# Alazab Data Hub

أنت مهندس برمجيات محترف مسؤول عن تحليل وتصميم وتنفيذ منصة مؤسسية مركزية باسم:

Alazab Data Platform

الهوية المؤسسية للمنصة:
data@alazab.com
https://data.alazab.com
الهدف الرئيسي:
إنشاء منصة مركزية موحدة لإدارة منظومة البيانات وقواعد البيانات الخاصة بالعزب، بحيث تصبح نقطة التحكم والحوكمة والمراقبة والربط ومعرفة مصادر البيانات لجميع الأنظمة، دون إجبار الأنظمة الحالية على الاندماج داخل قاعدة بيانات واحدة ودون كسر استقلال أي نظام قائم.

المطلوب ليس إنشاء Database جديدة تجمع بيانات الشركة كلها.

المطلوب إنشاء طبقة مؤسسية مركزية فوق مصادر البيانات الحالية والقادمة، تستطيع معرفة:
- ما الأنظمة الموجودة؟
- ما قواعد البيانات التابعة لكل نظام؟
- أين تعمل؟
- ما البيئة التابعة لها؟
- من يملكها؟
- من يستطيع الوصول إليها؟
- ما حالتها؟
- هل النسخ الاحتياطي يعمل؟
- هل النسخة الاحتياطية قابلة للاستعادة؟
- ما إصدار الـSchema الحالي؟
- ما التغييرات التي حدثت عليها؟
- ما العلاقات بينها وبين بقية أنظمة العزب؟
- ما الكيانات المشتركة بين الأنظمة؟
- كيف تحصل الأنظمة والذكاء الاصطناعي على البيانات بطريقة محكومة؟

==================================================
1. المبادئ الأساسية
==================================================

يجب الالتزام بالمبادئ التالية أثناء التصميم والتنفيذ:

1. عدم دمج جميع قواعد البيانات داخل قاعدة بيانات مركزية واحدة.

2. الحفاظ على استقلال الأنظمة الحالية.

3. عدم تنفيذ نقل أو Migration للأنظمة القائمة لمجرد توحيد الإدارة.

4. المنصة هي Control Plane وإدارة وحوكمة وربط، وليست بديلاً عن التطبيقات التشغيلية.

5. يجب أن تدعم المنصة تعدد أنواع ومواقع ومزودي قواعد البيانات ومصادر البيانات.

6. يجب أن تكون المنصة قابلة لإضافة أنظمة وقواعد بيانات جديدة مستقبلاً دون إعادة تصميم جوهري.

7. يجب الفصل الكامل بين:
   - System
   - Application
   - Environment
   - Database
   - Data Source
   - Identity
   - Credential
   - Owner

8. يجب عدم افتراض أي معلومات غير مثبتة عن البيئة الحالية.

9. قبل تنفيذ أي تكامل مع نظام قائم يجب اكتشاف وفحص وضعه الفعلي.

10. أي معلومة غير معروفة يجب تسجيلها كـUnknown بدلاً من تخمينها.

11. Production وStaging وDevelopment كيانات مستقلة ويجب عدم خلطها.

12. يجب أن يكون لكل عملية إدارية أو تغيير قابلية للتتبع والمراجعة.

==================================================
2. الأنظمة الحالية
==================================================

يجب تصميم المنصة لاستيعاب الأنظمة الحالية للعزب، ومنها على سبيل المثال:

- UberFix
- AzBIM
- ERPNext
- Products
- Auth
- Store
- AI systems
- Content Processing systems
- وأي أنظمة داخلية أو خارجية يتم إضافتها لاحقاً.

لا تعتبر القائمة السابقة حدوداً ثابتة للمنصة.

يجب أن يستطيع المسؤول إضافة System جديد من المنصة وربطه بمصادر بياناته وبيئاته وملاك النظام والمسؤولين عنه.

==================================================
3. البوابة المركزية
==================================================

يجب توفير بوابة إدارية مركزية تمثل واجهة Alazab Data Platform.

الهدف منها أن يستطيع المسؤول رؤية حالة منظومة البيانات بالكامل من مكان واحد.

يجب أن تحتوي البوابة على أقسام رئيسية تغطي على الأقل:

- Overview
- Systems
- Databases
- Data Sources
- Environments
- Master Data
- Integrations
- Monitoring
- Backups
- Restore Tests
- Schema Versions
- Migrations
- Identities
- Access Control
- Secrets Registry
- Incidents
- Audit Logs
- AI Data Access
- Platform Settings

لا تعتبر هذه أسماء واجهات إلزامية، وإنما قدرات مطلوبة داخل المنتج.

==================================================
4. Platform Overview
==================================================

يجب أن تقدم الصفحة الرئيسية صورة واضحة عن حالة المنصة بالكامل.

يجب أن يستطيع المسؤول معرفة أشياء مثل:

- إجمالي عدد الأنظمة.
- عدد قواعد البيانات.
- عدد مصادر البيانات.
- عدد بيئات Production.
- الأنظمة السليمة.
- الأنظمة التي تحتوي تحذيرات.
- الأنظمة الحرجة.
- حالة Monitoring.
- حالة Backup.
- حالة Restore Verification.
- حالة التكاملات.
- آخر الأحداث المهمة.
- آخر الأعطال.
- قواعد البيانات التي تحتاج تدخل.
- الأنظمة التي لم يتم فحصها حديثاً.

يجب ألا تكون Dashboard مجرد أرقام شكلية.

كل مؤشر يجب أن يؤدي إلى المصدر الفعلي الذي نتج عنه.

==================================================
5. Systems Registry
==================================================

يجب إنشاء سجل مركزي للأنظمة.

كل System يجب أن يكون كياناً مستقلاً داخل المنصة.

يجب أن يستطيع السجل الاحتفاظ بمعلومات مثل:

- الاسم.
- الكود.
- الوصف.
- الوظيفة.
- الحالة.
- الأهمية.
- Business Owner.
- Technical Owner.
- البيئات التابعة له.
- التطبيقات التابعة له.
- قواعد البيانات التابعة له.
- مصادر البيانات.
- التكاملات.
- التبعيات.
- معلومات التشغيل الأساسية.
- تاريخ الإنشاء.
- آخر مراجعة.

يجب أن يكون System قادراً على امتلاك أكثر من Database وأكثر من Environment وأكثر من Data Source.

==================================================
6. Database Registry
==================================================

يجب إنشاء Database Registry مركزي يمثل المصدر الرسمي لمعرفة قواعد بيانات العزب.

كل Database يجب أن يكون لها Record مستقل.

يجب أن يسمح Registry بتسجيل معلومات تشمل:

- معرف داخلي ثابت.
- اسم واضح.
- الكود.
- النظام التابع لها.
- البيئة.
- نوع قاعدة البيانات.
- موقعها.
- مزودها.
- المنطقة.
- Server أو Host.
- Port عند الحاجة.
- اسم قاعدة البيانات.
- Version.
- الحالة.
- مستوى الأهمية.
- Business Owner.
- Technical Owner.
- المسؤول عن التشغيل.
- سياسة النسخ الاحتياطي.
- سياسة المراقبة.
- آخر Backup.
- آخر Restore Test.
- آخر Health Check.
- Schema Version.
- Migration Version.
- معلومات الاتصال المرجعية.
- التبعيات.
- الملاحظات.
- تاريخ الإنشاء.
- تاريخ آخر تعديل.

لا يتم تخزين بيانات تشغيلية تخص التطبيقات داخل Database Registry.

وظيفته Metadata وإدارة وليس استبدال قواعد البيانات نفسها.

==================================================
7. Environment Management
==================================================

يجب أن تفهم المنصة مفهوم Environment بشكل مستقل.

يجب دعم بيئات مثل:

- Production
- Staging
- Development

مع إمكانية التوسع عند الحاجة.

يجب أن يستطيع المسؤول معرفة:

System
→ Environment
→ Applications
→ Databases
→ Data Sources

ويجب منع الالتباس بين قواعد Production وغيرها.

==================================================
8. Database Discovery
==================================================

يجب أن تحتوي المنصة على آلية لاكتشاف وتسجيل البيئة الحالية.

Discovery يجب أن يستطيع جمع المعلومات الفعلية المتاحة عن قواعد البيانات ومصادر البيانات.

الهدف:

تحويل البيئة الحالية من مجموعة موارد موزعة وغير موحدة إلى Inventory واضح وموثق.

يجب أن يوضح Discovery:

- ما تم اكتشافه.
- ما تم تسجيله.
- ما هو معروف.
- ما هو غير معروف.
- ما يحتاج بيانات إضافية.
- ما يبدو غير مستخدم.
- ما لا يمكن الوصول إليه.
- ما يحتاج مراجعة.

يجب عدم تعديل أو حذف أي مورد أثناء Discovery.

Discovery عملية قراءة وتحليل ما لم يتم إصدار أمر صريح بخلاف ذلك.

==================================================
9. Master Data
==================================================

يجب أن توفر المنصة طبقة Master Data مركزية للعزب.

هناك كيانات تتكرر عبر أنظمة متعددة مثل:

- Companies
- Clients
- Branches
- Locations
- Properties
- Projects
- Products
- Services
- Suppliers
- Assets
- Contracts
- Employees
- Technicians
- People

المشكلة المطلوب حلها:

قد يمثل نفس العميل أو الفرع أو المشروع أو المنتج بمعرف مختلف في أكثر من نظام.

يجب أن توفر المنصة معرفاً مؤسسياً عالمياً للكيان داخل العزب.

Global ID لا يلغي ID الخاص بالنظام الأصلي.

بل يجب الاحتفاظ بالعلاقة:

Global Entity
→ Source System
→ External ID

مثال منطقي:

Global Branch
    ├── UberFix ID
    ├── BIM ID
    └── ERP ID

يجب أن تستطيع المنصة معرفة أن السجلات الثلاثة تمثل نفس الكيان الحقيقي.

==================================================
10. Entity Mapping
==================================================

يجب إنشاء نظام واضح لربط الكيانات بين مصادر البيانات.

يجب دعم:

- إنشاء Global Entity.
- ربط External IDs.
- كشف العلاقات الموجودة.
- مراجعة الربط.
- دمج Mapping مكرر.
- اكتشاف Mapping المتعارض.
- تحديد Source of Truth.
- الاحتفاظ بتاريخ تعديلات Mapping.

لا يتم حذف معرفات الأنظمة الأصلية.

==================================================
11. Data Ownership
==================================================

لكل نوع من البيانات يجب أن يكون هناك مفهوم واضح لـ:

- Data Owner.
- Source System.
- System of Record.
- Authoritative Source.
- Consumers.

لا يجب أن تفترض المنصة أن النسخة الموجودة داخل Master Data هي دائماً المصدر الأصلي.

يجب الفصل بين:

Master Identity

و

Operational Data Ownership.

==================================================
12. Integration Management
==================================================

يجب أن تدير المنصة العلاقات والتكاملات بين الأنظمة.

يجب عدم إنشاء اعتماد فوضوي يجعل كل قاعدة بيانات تقرأ مباشرة من قواعد بقية الأنظمة.

يجب أن يكون كل Integration معروفاً ومسجلاً.

كل Integration يجب أن يحتوي على معلومات مثل:

- Source.
- Destination.
- Purpose.
- Direction.
- Data Scope.
- Owner.
- Status.
- Last Successful Run.
- Last Failure.
- Dependencies.
- Authentication Reference.
- Error State.

يجب أن تستطيع المنصة إظهار خريطة التبعيات بين الأنظمة.

==================================================
13. Central Data Access
==================================================

يجب توفير طبقة وصول محكومة للبيانات المشتركة.

الهدف أن تستطيع التطبيقات والأنظمة الحصول على البيانات المؤسسية المشتركة دون الحاجة لمعرفة التفاصيل الداخلية لكل Database.

يجب الفصل بين:

- الوصول التشغيلي المباشر الخاص بالتطبيق.
- الوصول المؤسسي المشترك.
- الوصول التحليلي.
- وصول الذكاء الاصطناعي.
- الوصول الإداري.

ويجب ألا يؤدي هذا إلى إنشاء قاعدة بيانات واحدة ضخمة لجميع التطبيقات.

==================================================
14. Monitoring
==================================================

يجب أن توفر المنصة مراقبة مركزية لحالة قواعد البيانات ومصادر البيانات.

يجب دعم متابعة مؤشرات مناسبة لكل مصدر، بما يشمل قدر الإمكان:

- Availability.
- Connectivity.
- Capacity.
- Storage.
- Connections.
- Query performance.
- Slow operations.
- Locks.
- Deadlocks.
- Replication.
- Errors.
- Backup status.
- Restore verification.
- Version.
- Health status.

ويجب تحويل النتائج إلى Status مفهوم مثل:

Healthy
Warning
Critical
Unknown

مع الاحتفاظ بسبب الحالة وليس اللون فقط.

==================================================
15. Alerts and Incidents
==================================================

عند حدوث مشكلة يجب أن تستطيع المنصة إنشاء Alert أو Incident.

يجب تسجيل:

- مصدر المشكلة.
- النظام.
- قاعدة البيانات.
- وقت البداية.
- مستوى الخطورة.
- السبب المعروف.
- الأدلة.
- الحالة الحالية.
- الشخص أو الفريق المسؤول.
- الإجراءات التي تمت.
- وقت الحل.
- نتيجة الحل.

يجب ربط Incident بالسجل والموارد الفعلية وليس تخزين نص غير مرتبط فقط.

==================================================
16. Backup Governance
==================================================

يجب إدارة النسخ الاحتياطية من المنصة بصورة مركزية.

لكن يجب الفصل بين:

Backup Policy

و

Backup Execution.

يجب أن تستطيع المنصة معرفة لكل Database:

- هل Backup مطلوب؟
- ما السياسة؟
- هل التنفيذ يعمل؟
- متى آخر Backup؟
- هل نجح؟
- ما مدة الاحتفاظ؟
- أين يوجد؟
- هل توجد نسخة خارج بيئة التشغيل؟
- هل تمت تجربة Restore؟

==================================================
17. Restore Verification
==================================================

وجود Backup لا يعتبر دليلاً على إمكانية استعادة البيانات.

يجب أن تحتوي المنصة على سجل مستقل لـRestore Tests.

يجب أن يستطيع المسؤول معرفة:

Backup Exists: Yes/No

Restore Verified: Yes/No

وأن تكون هناك معلومات مثل:

- Backup المستخدم.
- Database.
- تاريخ الاختبار.
- نتيجة الاختبار.
- المدة.
- الشخص أو العملية التي نفذت الاختبار.
- الأخطاء.
- ملاحظات التحقق.

==================================================
18. Schema Management
==================================================

يجب أن تعرف المنصة Schema Version الخاص بكل Database حيث يكون ذلك منطبقاً.

يجب أن يكون هناك سجل تاريخي للتغييرات.

يجب أن تستطيع معرفة العلاقة بين:

System Version
Application Version
Database Schema Version
Migration

يجب ألا تصبح التغييرات غير الموثقة هي الطريقة الطبيعية لإدارة Production.

==================================================
19. Migration Registry
==================================================

كل Migration مهمة يجب أن يكون لها سجل.

يجب أن يشمل:

- System.
- Environment.
- Database.
- Migration ID.
- From Version.
- To Version.
- Status.
- Applied At.
- Applied By.
- Related Change.
- Result.
- Error إن وجد.
- Rollback status عند توفره.

الهدف هو معرفة ماذا تغير ومتى ولماذا.

==================================================
20. Identity Management
==================================================

يجب الفصل بين:

Human Identity

و

Service Identity.

الحساب المؤسسي:

data@alazab.com

يمثل ملكية وإدارة Alazab Data Platform.

أما التطبيقات والخدمات فيجب أن تكون لها هويات تشغيلية منفصلة.

يجب أن تستطيع المنصة معرفة:

- من يملك الهوية.
- ما نوعها.
- لأي System تتبع.
- لأي Environment.
- ما مستوى الوصول.
- متى تم إنشاؤها.
- آخر استخدام.
- حالتها.

==================================================
21. Access Control
==================================================

يجب توفير نظام صلاحيات واضح.

يجب دعم أدوار وظيفية مثل:

- Platform Owner.
- Platform Administrator.
- Database Administrator.
- Data Engineer.
- Application Owner.
- Integration Manager.
- Analyst.
- Read Only.

ولا تعتبر هذه القائمة نهائية.

يجب تطبيق مبدأ أقل صلاحية لازمة.

ويجب الفصل بين صلاحيات إدارة المنصة وصلاحيات قواعد البيانات نفسها.

==================================================
22. Secrets Registry
==================================================

يجب توفير Registry مركزي لمعرفة الأسرار والCredentials التابعة للأنظمة.

المطلوب ليس بالضرورة أن تكون القيمة السرية نفسها موجودة داخل قاعدة بيانات المنصة.

لكن يجب أن تستطيع المنصة معرفة:

- Secret ID.
- System.
- Environment.
- Purpose.
- Owner.
- Storage Location.
- Rotation Policy.
- Last Rotation.
- Expiration.
- Status.

لا يتم عرض القيم السرية في صفحات الإدارة العامة.

==================================================
23. Audit
==================================================

جميع العمليات الإدارية الحساسة يجب أن تكون قابلة للمراجعة.

Audit يجب أن يجيب:

Who
What
Where
When
Before
After
Result

ويشمل على الأقل:

- تغييرات Registry.
- الصلاحيات.
- Credentials metadata.
- Migrations.
- Master Data mappings.
- Integrations.
- Backup policies.
- Restore verification.
- Platform settings.

==================================================
24. AI Data Access
==================================================

يجب اعتبار أنظمة ووكلاء الذكاء الاصطناعي Consumer منفصل للبيانات.

لا يتم منح AI Agents وصولاً غير مقيد إلى Production databases لمجرد حاجتهم للبيانات.

يجب توفير طبقة وصول محكومة تستطيع تحديد:

- ما البيانات التي يستطيع Agent رؤيتها.
- ما العمليات المسموح بها.
- هل الوصول Read Only أم Write.
- Source System.
- Global Entity relationships.
- Audit لكل عملية حساسة.
- حدود الوصول حسب النظام والبيئة.

يجب تصميم هذه الطبقة بحيث تصبح أساساً لاستخدام بيانات العزب في:

- AI Agents.
- Search.
- Knowledge retrieval.
- Analytics.
- Automation.
- Decision support.

==================================================
25. Knowledge and Vector Data
==================================================

يجب اعتبار بيانات البحث الدلالي والمعرفة والتمثيلات المتجهية طبقة بيانات مستقلة منطقياً عن قواعد التشغيل.

يجب الحفاظ على الربط بين أي Knowledge Record وبين مصدره الأصلي.

يجب الاحتفاظ بمعلومات مثل:

- Source System.
- Source ID.
- Global Entity ID إن وجد.
- Document ID.
- Content Type.
- Metadata.
- Version.
- Created At.
- Updated At.

حتى لا تتحول بيانات الذكاء الاصطناعي إلى نسخة غير قابلة للتتبع من بيانات الشركة.

==================================================
26. Data Lineage
==================================================

يجب أن تستطيع المنصة تتبع أصل البيانات قدر الإمكان.

مثلاً:

هذا السجل:
→ جاء من أي System؟
→ من أي Database؟
→ من أي Entity؟
→ هل تم تحويله؟
→ أين تم استهلاكه؟
→ هل توجد نسخة أخرى منه؟

الهدف الوصول تدريجياً إلى Data Lineage واضح للبيانات المهمة.

==================================================
27. Dependency Mapping
==================================================

يجب توفير تصور للعلاقات بين الأنظمة.

مثلاً:

System A
→ يستخدم Master Data
→ يرسل بيانات إلى System B
→ يعتمد على Database C

MariaDB 11.8.x

Redis 8.8.x

Prisma ORM 7.x
